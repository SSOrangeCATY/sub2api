# Cyber Policy 用户限制设计

## 已确认的业务规则

同一平台用户的所有 API Key 共用一个滚动统计窗口。默认最近 7 天内命中 2 次，暂停 API 调用 24 小时；命中 3 次，持续暂停，必须由管理员填写原因解除。窗口、门槛、临时暂停小时数和管理员解除方式都可在页面配置。

临时到期不清零窗口内计数。因此到期后再次命中，仍可能在七天窗口内达到第三次。第二次判定前已经准入的并发请求，也可以在完成时把第二次的临时限制升级为第三次的管理员解除限制。被拦截的后续请求不会因为没有访问上游而虚增命中。

限制作用于 API 访问。网站账户与联系管理员入口保留。管理员维护的 users.status 独立生效，自动到期和策略解除都不会恢复被其他原因停用的基础账户。

## 通用框架与当前适配器

通用仓储使用 policy_key、scope、generation 和配置版本区分策略与计数周期。当前服务端适配器固定使用 cyber_policy / api；客户端不能通过传入另一个策略键来解除其他限制。新增策略应实现事件识别、准入和配置适配，复用同一账本、版本解除、查询和到期机制。

256_user_risk_policy_ledger.sql 只新增通用表及索引：

| 表 | 职责 |
| --- | --- |
| user_risk_cycles | 用户与策略的当前计数代际 |
| user_risk_events | 唯一逻辑事件、准入时间、持久化时间、精简策略快照与已提交决策 |
| user_risk_restrictions | 独立访问范围、限制版本、处罚时次数、门槛、开始和解除时间 |
| user_risk_actions | 命中、限制、升级、到期、解除和忽略的不可变动作快照 |

首次上线不从历史审核日志追溯处罚用户，也不批量改变基础账户状态。未发布的 Cyber 专用表和旧准入原型已移除。

## 准入、去重与同步顺序

HTTP 准入和 WebSocket 每个逻辑请求的准入由服务端产生事件标识，并捕获计数代际。一个逻辑请求在安全账号重试中保持同一事件标识。WebSocket 上游代理重入可能重置局部 turn 数字，因此身份生命周期由请求完成与安全 failover 决定，不能只比较局部序号。

首帧必须在握手后的实际请求到达时重新检查限制。后续帧也重新检查；握手时的缓存不能允许新受限用户继续调用。无法读取限制状态时拒绝继续准入。已有 Cyber 观察无法持久化时，连接上的后续请求保持失败围栏。

只有已识别的上游结构化 Cyber Policy 拒绝进入适配器。正常成功正文中的相同词语不构成命中。网关同步等待账本决策，然后才允许下一轮继续；邮件和补充审核日志在该决策之后处理，不重新执行处罚。

同一用户使用固定的用户、计数代际、限制锁顺序。计数使用数据库的持久化判定时间。重复事件返回原有已提交结果，不因后续配置变化重新计算。决策快照只保留相关规则，不包含审核 API 密钥等无关配置。

## 规则配置与优先级

风险总开关、分组和模型范围、可信用户豁免及独立规则开关决定新的策略观察。配置与豁免使用新的权威读取，调用方旧的 LogOnly 提示不能保留已经撤销的豁免。仓储在用户锁下复核平台角色。

普通内容审核的自动处罚固定排除 Cyber 事件。cyber_policy_exclude_from_ban_count 仅为历史配置兼容保留，修改它不会切回旧处罚路径。

配置支持 1–30 天窗口、1–8 条阶梯规则、递增且不超过 1000 的门槛，以及 1–720 小时临时暂停。管理员解除规则只能在最后，不能同时填写自动期限。关闭规则停止新的自动处置，已有有效限制仍需到期或明确解除。

保存携带 expected_revision。仓储在自己拥有的事务中校验旧版本并保存下一个版本；旧格式空配置、缺失或零版本按版本 1 读取。范围变更与配置版本保持一致。运行时不接受较旧版本覆盖新配置。

## 到期与管理员解除

临时到期只结束该策略的限制，保留计数和审计。到期访问判断不依赖清理任务及时执行。

管理员解除要求认证主体、有效管理员身份、操作标识、当前限制版本和原因。仓储再次复核这些条件。解除推进 generation，保留事件及动作历史。旧代际已经准入但延迟完成的事件保留为历史，不计入新周期。旧解除操作重放只能返回原结果，不能解除后来产生的新限制。

页面在发送前冻结操作标识、版本和原因。网络结果不明确时只重试原操作；不能在重试时悄悄更换原因或目标。版本冲突后保留原因，重新读取当前处罚，展示新的方式、范围、门槛和期限，再等待管理员重新提交。解除成功仍依据返回的基础账户状态提示是否存在独立停用。

## 查询与页面

入口为安全审计中的风控中心，页面分为内容审核、用户限制和处置记录。用户限制依次展示已保存规则、草稿编辑及后果预览、当前限制。

当前窗口次数与处罚时次数分别展示。记录携带查询时间及当时配置版本。列表游标绑定查询类型、筛选与页大小；改变草稿页大小不会改变旧游标的查询参数，应用筛选回到第一页。

每页在短只读 REPEATABLE READ 事务中读取；跨页是实时遍历，不是冻结的结果集。并发提交或状态变化后，完整查看最新成员需要刷新第一页，不能用总数推断一个不存在的下一页。

## 关联业务与发布边界

QQ 身份绑定、福利资格、积分、兑换、支付账本与风险限制保持各自所有权。风控操作不删除这些记录。关联复查见 QQ_WELFARE_FALLBACK_REVIEW.md。

请求前监控选组、组内账号重试和同一请求跨组重放是不同能力。当前路由不保证同一请求失败后自动进入下一兜底组；Cyber 拒绝不应成为重放提示的触发条件。

迁移为新增结构，但更旧镜像不能自动识别这套限制账本。回滚时必须核对旧镜像的访问保护能力；不能把旧镜像能启动等同于新限制继续生效。保留账本和上线后的业务数据，不通过恢复旧数据库覆盖新请求记录。

本地定向验证与静态复审通过不等于已上线。发布仍须经过 custom/main 和 production 的受保护 PR、必需检查、精确生产提交镜像、构建产物 digest 关联、部署健康与真实请求检查。
