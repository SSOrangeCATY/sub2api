# QQ、福利与兜底分组复查

## QQ 与福利的职责

QQ 机器人管理负责连接、群策略与身份认证；网站绑定以已认证的网站用户为主体。机器人请求不能使用网站专属福利兑换路径。身份绑定通过用户锁与唯一约束处理并发。

福利中心负责签到、积分、付费资格、商品、库存、兑换及核销记录。兑换在用户、福利账户与商品锁下更新积分、库存、余额和账本，并在同一事务提交。付费资格来自付费来源记录，赠送来源保持赠送语义。

本轮静态复查没有确认身份串绑、并发核销或重复账本的确定性缺陷。幂等请求参数指纹可以作为后续改进，不应据此声称现有路径已经存在重复扣费漏洞。发布保留现有 QQ 门禁配置，不用过时运维说明覆盖线上设置。

用户风险限制拥有独立账本和 API 访问范围，不删除 QQ 绑定、福利、积分或支付历史。基础账户状态、QQ 验证和风险限制各自生效。

## 当前兜底能力

请求进入前，监控路由可以依据健康状态选择业务目标分组。选定分组内仍可执行已有的账号调度与安全失败重试。这不能证明同一次请求失败后会自动跨入下一个兜底分组。

因此页面与发布说明必须区分请求前健康选路、组内账号轮转、请求内跨组重放。当前实现不承诺第三项。Cyber Policy 拒绝不应被当成连接故障并向其他组重放同一提示。

## 如果扩展为请求内跨组重试

请求级协调器需要保留入口身份与权限，并维护候选目标、已尝试目标和总尝试上限。每次切换目标重新建立模型映射、准入、额度、价格、并发预留和最终日志上下文；不能只替换 group_id。

只允许能够证明可安全重放且尚无用户可见输出的失败。存在已输出内容、未知副作用、固定资源归属或不明扣费状态时停止。WebSocket 会话、previous_response_id 与固定上游资源不能凭空迁移。

Cyber Policy 与其他明确业务拒绝不触发跨组重放。重试也不能绕过入口用户的分组权限。整个逻辑请求只能最终结算一次，失败尝试释放自己的预留资源，尝试记录与最终账单保持对应。

新增该能力前应覆盖首输出超时、连接故障、候选耗尽、取消、部分流输出、价格差异、并发预留释放及账本幂等回归。记录只保存必要的脱敏元数据，不通过日志复制完整用户提示或凭据。
